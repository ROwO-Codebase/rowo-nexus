# Relying-Party Integration

Nexus proves cryptographic control; it does not create an RP account. The RP owns its challenges,
protected resources, abuse policy, acceptance receipts, and any short-lived local session created
after proof verification.

## Browser flow

1. The RP backend creates a random, single-use challenge for one action and resource, expiring
   within 120 seconds.
2. The RP SDK opens the dedicated wallet origin.
3. The wallet accepts a typed proof request and treats `MessageEvent.origin` as the authoritative
   audience.
4. The wallet shows the requesting origin, local identity label, action, resource, and any
   cross-scope warning.
5. On explicit approval, it signs a proof with `aud = event.origin`.
6. It replies only through `event.source.postMessage(result, event.origin)`.
7. The RP frontend submits the proof to its backend.
8. The backend verifies the proof, live/fresh lifecycle state, and challenge, then atomically
   consumes the nonce with the protected operation.

The request API does not accept an authoritative `aud`. Proof responses never use wildcard
`postMessage`. The wallet does not reveal its complete identity list to an RP.

## Challenges

Store only an opaque challenge ID, nonce hash, exact action/resource, expiry, and optional
consumption time. Nonces contain at least 128 random bits and are generated by a CSPRNG. A nonce
cannot be reused for a different action or resource.

## Resource ownership

Applications store immutable `resource.author_subject = nx1_...`, not `nexus_user_id`, controller,
vault, or civil-identity foreign keys.

For creation, allocate a provisional resource ID, issue a challenge for the exact create operation,
verify proof and lifecycle, then persist the resource, author subject, and accepted-proof hash. For
edit/delete, read the immutable author subject, issue a resource-specific challenge, and require
proof by the same currently active subject.

Do not offer a generic endpoint that lets a new key claim an old resource. If durable historical
authorship matters, issue a signed RP acceptance receipt at creation rather than trusting a later
self-asserted timestamp.

## Verification package

`@nexus/verifier` is binding-free and suitable for Node, Deno, Bun, Workers, and other Web
Crypto-capable runtimes. It verifies subjects, ownership proofs, registry receipts, and status
statements. RP code chooses and documents one lifecycle policy: `strict`, bounded `session`, or
valid `stapled-status`.

Nexus does not need to observe subsequent requests made under an RP-local session.

For an explicitly negotiated `nexus.ownership-proof.v2`, the RP additionally verifies the embedded
root authorization and device signature and obtains fresh status for the exact subject, `nxd2_`
device, and `nxa2_` authorization. A v1 subject-only status statement is insufficient. V2 sessions
retain those identifiers so sibling or root revocation of that device can terminate its authority.
The RP passes an explicit expected `contextHash` or `null`; omission is not an "accept anything"
mode. A device authorization is expired at `now >= expiresAt`, regardless of a still-valid cached
status statement. See the [v2 root/device profile](./device-delegation-v2.md).

## Cross-origin tests

Browser E2E uses two distinct origins and proves that one cannot request or replay a proof for the
other, spoof `aud`, receive proof responses intended for the other, or enumerate the other's scoped
identity choices. Network inspection must show that private keys and revocation secrets never leave
the wallet.
